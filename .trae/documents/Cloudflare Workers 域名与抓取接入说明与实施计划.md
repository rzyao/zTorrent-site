**简要回答**

* Workers 的“入口域名”是可配置且稳定的：

  * 默认使用 `*.workers.dev`，你在账号下创建一个子域名后即固定（除非你主动更改）。

  * 也可以绑定你自己的自定义域名或路径路由（如 `mirror.example.com/*`），配置后同样是稳定的入口。

* 固定的是入口域名，不是“出网 IP”：

  * Worker 抓取豆瓣时，请求从 Cloudflare 的边缘节点发出，源 IP 来自 Cloudflare 的全球 IP 池，非单一固定 IP；因此不会再命中“后端固定 IP 被限”的同类问题。

  * 但若豆瓣对 Cloudflare IP 段整体有限制，仍需通过限速、缓存、退避或改用 Cloudflare Images 的 URL 上传来降低风险。

**实施计划**

* 域名绑定与路由

  * 选择入口：`<subdomain>.workers.dev` 或绑定自定义域名（如 `mirror.example.com`）。

  * 在 Cloudflare 控制台为自定义域配置路由（例如 `mirror.example.com/*` 指向该 Worker）。

* Worker 抓取逻辑

  * 白名单校验：仅允许 `douban.com`、`doubanio.com` 等域。

  * 头部与限流：设置 `User-Agent` 与可选 `Referer: https://movie.douban.com/`；限制重定向次数、响应大小（如 ≤10MB）、仅图片 MIME。

  * 退避策略：对 429/403/5xx 做指数退避与有限重试，避免被目标站进一步限流。

* 存储与返回

  * 方案一：写入 R2，按内容哈希命名（去重），返回稳定访问 URL（可通过 Worker 再代理读取或直接公开 R2）。

  * 方案二：将图片字节流回传你后端，由后端落存并进入现有缩略图流水线。

* 前端集成

  * 在上传页与编辑页（海报/剧照/封面字段）调用后端“镜像接口”，用返回的站内地址替换外链。

  * 保持现有缩略图管线与展示逻辑不变（`ThumbCoverPath`/`MediumCoverPath` 等）。

* 缓存与可观测

  * 在 Worker 使用 Cache API 或 `cf: { cacheTtl }` 对抓取结果做边缘缓存，降低重复命中豆瓣。

  * 记录抓取成功率、耗时与失败分布，便于调优限速与重试策略。

* 验证与安全

  * 单元/集成测试：域名校验、类型大小限制、错误分支；

  * 端到端：豆瓣样本链接→抓取→存储→缩略图→前端展示全链路；

  * 合规：持久化来源 URL 与时间，提供投诉处理与手动删除能力
