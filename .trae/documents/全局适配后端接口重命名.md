**目标**

* 全面适配后端接口重命名，确保现有页面、Hooks、Store 的 API 调用与返回数据结构在新的 OpenAPI 规范下均可正常工作。

**现状与影响面**

* 项目使用 `openapi-typescript-codegen` 生成的 axios 客户端，统一入口在 `src/api/index.ts`，核心请求封装在 `src/api/core/request.ts`，全局配置在 `src/api/core/OpenAPI.ts`。

* 业务层主要通过以下 Service 调用 API（列出当前使用点，便于逐一适配）：

  * `src/pages/TorrentDetailPage/index.tsx:131` 使用 `TorrentsService.torrentsControllerGet`

  * `src/pages/TorrentDetailPage/index.tsx:160` 映射字段 `downloadUrl`（与后端字段名变更强相关）

  * `src/pages/TorrentDetailPage/index.tsx:320` `window.open(torrentData.downloadUrl, '_blank')`

  * `src/pages/UploadTorrentPage.tsx:119/135` 使用 `ImagesService.imagesControllerUpload`

**实施步骤**

* 步骤1：更新 OpenAPI 客户端

  * 运行生成脚本 `npm run api:generate`（从新后端 `api-docs-json` 拉取最新接口定义），同步 `src/api` 下 Service/Model 的命名变更。

  * 原因：统一来源的代码生成可以一次性反映所有重命名，避免手工遗漏，并保证请求路径、方法、类型与后端一致。

* 步骤2：编译并抓取所有类型与符号错误

  * 执行前端编译，捕获因重命名导致的 `import`、方法名、参数/返回类型不匹配的错误位置。

  * 原因：编译器可作为“变更雷达”，精确定位所有受影响的调用点，指导逐一修复。

* 步骤3：逐文件适配 Service 方法重命名

  * 依据编译错误与上面的使用清单，逐一把旧方法名替换为新方法名（如 `torrentsControllerGet → 新名称`），并在修改处补充详细注释，说明：

    * 旧方法名、对应新方法名、后端变更原因（来自新 OpenAPI 的 operationId/path 变化）

    * 参数结构调整点（例如 `page/pageSize` 重命名为 `limit`/`order` 等）

  * 原因：保证调用符号层面的兼容，防止运行时 404 或 400。

* 步骤4：适配返回数据结构映射

  * 聚焦自定义映射代码，尤其是：

    * `src/pages/TorrentDetailPage/index.tsx:134-161` 将后端 `data` 映射到 `TorrentData`。核对如 `downloadUrl`、`fileList`、`mediaInfo`、`relatedTorrents` 等字段的命名/层级变化并同步更新。

    * `src/pages/TorrentsPage.tsx:114-116` 列表数据 `items/total` 的命名与分页字段，确保 UI 统计与分页逻辑不变。

    * 其他页面的 `code/message/data` 包装处理保持兼容（当前已对包裹与直出两种响应做了容错处理）。

  * 原因：接口重命名往往伴随 DTO 字段调整；若字段名或层级变化未同步，UI 会显示空白或报错。

* 步骤5：统一 OpenAPI 配置与令牌注入

  * 复核 `OpenAPI.BASE` 与 `OpenAPI.TOKEN` 的设置位置（`src/hooks/useApi.ts:4-7` 和全局布局处），必要时更新为新的后端域名或认证策略。

  * 原因：后端升级可能伴随域名/路径或认证方式变化，需确保所有请求正确拼接与带上 Token。

* 步骤6：端到端验证

  * 启动前端开发服务，按以下页面验收：

    * 详情页：`TorrentDetailPage` 正常拉取并可点击 `下载`（`window.open` 调用字段存在且可用）。

    * 列表页：`TorrentsPage` 分类加载、分页与排序均正常。

    * 上传页：图片上传、InfoHash 校验与上传表单提交流程正常。

    * 注册/登录：验证码、注册与登录流程可用并能写入/读取 `accessToken`。

    * 字典数据：`dictionaryStore` 能正确加载并驱动 UI。

  * 原因：覆盖主要用户路径，确保接口适配后的功能完整性。

**代码修改时将添加的详细注释规范**

* 在每个改动点紧邻代码处添加中文注释，包含：

  * 接口重命名说明（旧名→新名、后端变更依据：operationId/路径）

  * 参数与返回结构变更点（新增/移除/重命名字段）

  * 对 UI 与逻辑的影响与兼容处理策略（例如回退值、空值处理）

**注意事项**

* 优先修改现有文件，不额外创建新文件；仅当需要引入兼容层时，才在 `src/api` 保持生成代码不改、在业务层最小范围内添加轻量适配。

* 保持安全实践：不在日志中输出敏感令牌；不改动 `OpenAPI` 的 Token 读取策略，除非后端认证方案确实变更。

* 若后端返回包装（`{ code, message, data }`）去除，将保留现有容错逻辑，优先以直出体为准。

**交付结果**

* 已更新的调用点与映射代码，所有页面编译通过并实际运行验证通过。

* 代码中补充完整注释与变更说明，便于后续维护与回溯。
