# 接口需求文档生成器 (前端视角)

此工作流用于在 **前端功能开发 / 页面设计** 阶段，帮助前端开发者梳理业务逻辑，参考业内最佳实践，并生成标准化的 **后端接口需求文档**。

这份生成的文档将作为后端开发的直接输入，确保后端 API 的设计完全符合前端的展示与交互需求，并严格遵循项目的接口规范。

## 执行步骤

### 1. 场景分析与功能梳理

仔细分析当前对话上下文、已有的前端页面代码或功能描述：

- **页面功能点**: 用户在页面上能做什么（增删改查、排序、过滤、特定业务操作）？
- **数据需求**: 页面需要展示哪些数据？哪些是动态加载的？
- **交互流程**: 点击按钮后需要触发什么操作？需要哪些参数？

### 2. 业内通用方案参考 (Best Practices)

// turbo
分析类似功能的通用实现方案（例如：如果不确定某个功能如何设计接口，可以参考常规做法）：

- 分页查询通常包含 `page`, `limit`, `sort`, `filter`。
- 敏感操作可能需要二次确认或验证码。
- 高频更新数据可能需要 WebSocket 或轮询。

### 3. 此项目接口规范校验

严格遵守 `docs/统一响应与异常拦截机制.md` 中的规范：

- **请求方法**: 业务接口统一使用 **POST**。
- **参数传递**: 所有参数通过 Body (DTO) 传递。
- **参数命名**:
  - API 接口 (Request/Response) 字段名：**camelCase** (小驼峰)。
  - 数据库字段通常是 snake_case，但接口层面必须转为 camelCase。
- **响应结构**: 必须符合 `{ code, message, data, path, timestamp }`。
  - **成功**: `code=1000`, `message` 通常为 'ok' 或 '操作成功'。
  - **业务异常 (BusinessException)**: HTTP 200, `code` 为业务错误码, `message` 为**展示给用户的友好提示**。
  - **系统/校验异常**: HTTP 4xx/5xx (或被拦截), `data.message` 包含底层具体报错原因（前端仅在调试时查看）。

### 4. 生成接口需求文档

在 `docs/api-requirements/` 目录下创建一个新的 Markdown 文件，命名格式为 `YYYY-MM-DD_<功能模块名>_需求文档.md`。

文档结构模板如下：

````markdown
# <功能模块名称> - 接口需求文档

> 提交日期: YYYY-MM-DD
> 对应页面/组件: (例如：用户管理页、评论组件)

## 1. 需求概述
````

## 5. 异常情况处理

列出前端需要特殊处理的错误场景：

- **业务异常 (BusinessException)**:
  - 场景：库存不足、权限不够、状态不符。
  - 预期行为：后端返回 HTTP 200 + code != 1000。`message` 字段直接用于 Toast 提示用户。
- **系统/校验异常**:
  - 场景：参数缺失、数据库连接失败。
  - 预期行为：`GlobalExceptionFilter` 会统一处理，前端通常拦截到 code=9xxx。调试时查看 `data.message` 获取详情。

```
## 注意事项

1. **命名规范**: 严禁在接口参数中使用 `snake_case`，必须强制转换为 **camelCase**。
2. **单一职责**: 每个接口应只做一件事，避免大而全的上帝接口。
3. **Mock 支持**: 如果需要，可以在文档中附带 Mock 数据示例，方便前端先行开发。
```
