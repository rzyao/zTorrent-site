# 论坛编辑器草稿功能 (Composer Drafts) 产品需求文档

## 1. 项目背景与目标

为了提升用户在论坛发帖和回复时的体验，防止意外关闭、页面刷新或跳转导致的内容丢失，需参照 Discourse 实现完善的客户端草稿机制。

**主要目标**：

1. **防止数据丢失**：自动保存用户的编辑内容。
2. **多上下文支持**：允许用户在不同话题下保留独立的草稿，互不干扰。
3. **状态持久化**：即使关闭浏览器，再次打开时也能恢复之前的编辑状态。

## 2. 核心逻辑

### 2.1 草稿键 (Draft Key) 设计

系统需基于当前的操作上下文维护一份草稿字典（Drafts Dictionary）。

| 场景           | 草稿 Key                | 说明                                                                                                   |
| :------------- | :---------------------- | :----------------------------------------------------------------------------------------------------- |
| **创建新话题** | `create_topic`          | 全局唯一，用于存储"创建新话题"的内容。                                                                 |
| **回复话题**   | `reply_topic_{topicId}` | 每个话题独立一个草稿。用于"回复话题"或"回复楼层"。                                                     |
| **编辑帖子**   | `reply_topic_{topicId}` | 根据用户要求，编辑帖子共享该话题的回复草稿空间（注：这意味着同一话题下的编辑和回复共享一个草稿槽位）。 |

### 2.2 草稿生命周期

#### A. 创建/恢复 (Open)

- 当用户打开编辑器时，系统根据当前模式和 `topicId` 生成 **Key**。
- 检查本地存储中是否存在该 Key 对应的草稿数据。
- **如果有草稿**：自动填充编辑器内容（标题、正文、分类、引用等）。
- **如果是新操作**：初始化为空白状态。

#### B. 更新 (Update)

- 用户的任何输入（标题输入、正文输入、添加引用）都应实时（或防抖）更新到当前 Key 对应的草稿存储中。
- **持久化策略**：草稿应立即写入 `localStorage`，确保浏览器奔溃也能恢复。

#### C. 保留 (Close)

- 点击编辑器右上角的 **"关闭 (X)"** 按钮，或点击"最小化"按钮。
- **行为**：仅关闭编辑器 UI 界面，**不删除**草稿数据。
- 用户下次再次点击回复该话题时，内容应原样重现。

#### D. 清除 (Discard / Submit)

草稿仅在以下两种情况下被物理删除：

1. **用户主动舍弃**：点击编辑器左下角的 **"舍弃"** 按钮。
2. **发布成功**：后端 API 返回成功响应后，自动清除当前对应的草稿。

#### E. 过期策略

- **策略**：**从不过期 (Never Verify)**。
- 除非用户主动清除或发布成功，否则草稿将一直保留在本地存储中。

## 3. 功能需求详情

### 3.1 状态管理变更 (ComposerStore)

需要重构 `ComposerStore` 的数据结构，从单一的 `draft` 对象改为支持多草稿管理。

**旧结构**：

```typescript
{
  draft: ComposerDraft;
}
```

**新结构建议**：

```typescript
{
  // 当前正在编辑的草稿（用于 UI 绑定）
  currentDraft: ComposerDraft;

  // 持久化的草稿字典
  drafts: Record<string, ComposerDraft>;

  // 核心 Action
  loadDraft: (key: string) => void;
  saveDraft: (key: string, data: Partial<ComposerDraft>) => void;
  clearDraft: (key: string) => void;
}
```

### 3.2 UI 交互变更

1. **"取消"按钮重命名**：
   - 将原有的 "取消" 按钮文案改为 **"舍弃"**。
   - 点击"舍弃"时，触发 `clearDraft` 并关闭编辑器。
2. **"关闭"按钮行为**：
   - 保持现有 UI 不变。
   - 点击时仅触发 `close()`，不清除数据。

3. **引用 (Quote) 处理**：
   - 引用列表 (`quotes`) 也必须作为草稿的一部分被持久化。
   - 恢复草稿时，需同步恢复已添加的引用卡片。

## 4. 技术实现建议

1. **Zustand Persistence**：
   - 继续使用 `persist` 中间件。
   - 确保存储结构能够序列化 `drafts` 字典。

2. **Key 生成工具函数**：
   - 封装 `getDraftKey(mode: string, topicId?: string): string` 函数，确保 Key 生成逻辑统一。

3. **防抖保存**：
   - 虽然 Zustand 更新很快，但为了性能，建议在写入 `localStorage` 层（即 `persist` 的触发）或输入监听层做轻微防抖（如 300ms）。

## 5. 验收标准 (Acceptance Criteria)

1. **场景一：回复中途退出**
   - 用户在话题 A 输入 "Hello World"。
   - 用户点击右上角关闭按钮。
   - 用户刷新页面。
   - 用户再次点击话题 A 的回复按钮。
   - **结果**：编辑器打开，内容显示 "Hello World"。

2. **场景二：多话题切换**
   - 用户在话题 A 输入 "Draft A"。
   - 用户导航到话题 B，点击回复，输入 "Draft B"。
   - 用户回到话题 A，点击回复。
   - **结果**：编辑器显示 "Draft A"（不显示 "Draft B"）。

3. **场景三：舍弃草稿**
   - 用户在话题 A 输入 "Wrong Text"。
   - 用户点击左下角 "舍弃"。
   - 编辑器关闭。
   - 用户再次点击回复。
   - **结果**：编辑器打开，内容为空。

4. **场景四：发布成功**
   - 用户输入内容并点击 "发布"。
   - 发布成功提示出现。
   - 用户再次点击回复。
   - **结果**：编辑器打开，内容为空（通过验证草稿自动清除）。
