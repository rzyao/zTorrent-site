# 求种功能蓝图

## 背景与现状
- 已有“发布求种”前端界面与最小校验，数据为静态假数据，未对接后端与状态流转。
- 关键代码位置：
  - 页面入口：`src/routes/AppRoutes.tsx:266-269` 路由 `'/requests'` 使用 `PermissionRoute` 权限守卫。
  - 页面主体：`src/pages/RequestsPage.tsx:63` 导出 `export function RequestsPage()`，包含 `list / create / detail` 三视图与占位提交流程。
- 已有通用 API 能力与积分模块封装：
  - OpenAPI 请求基座：`src/api/core/*`
  - React Query 提供器：`src/providers/QueryProvider.tsx:1-29`
  - 积分封装示例：`src/api/custom/bonus.ts:1-84`

## 目标与范围
- 完成“发布→认领→上传关联→用户验证→结算/仲裁→归档”的闭环功能，打通前后端与站内通知。
- 建立可审计、可风控、可监控的求种子系统，与 Bonus 积分联动，保障公平与安全。

## 角色与权限
- 角色：
  - 请求者（发起与验收）、应答者（认领与提交）、版主（仲裁与强制流转）、系统（定时到期、风控）
- 权限建议（后端返回权限字符串，与路由守卫对齐）：
  - `request:create`、`request:cancel`、`request:increase_bounty`
  - `request:claim`、`request:submit`、`request:link_torrent`
  - `request:verify`、`request:dispute`、`request:moderate`
  - `bonus:freeze`、`bonus:payout`、`bonus:release`
- 原因：明确权限边界，便于前端按钮显隐与后端校验，配合 `PermissionRoute` 实现细粒度访问控制。

## 生命周期与状态机
- 状态枚举：`draft → open → claimed → fulfilled_pending_verify → fulfilled → expired → cancelled → disputed`
- 主要流转：
  - 发布：`draft → open`（冻结悬赏）
  - 认领：`open → claimed`（并发/幂等控制）
  - 提交：`claimed → fulfilled_pending_verify`（关联种子/外链/证明）
  - 验证：`fulfilled_pending_verify → fulfilled`（发放悬赏）或 `→ disputed`（进入仲裁）
  - 到期：`open/claimed → expired`（自动解冻）
  - 取消：`open → cancelled`（规则校验后解冻）
- 原因：拆分人机动作与系统动作，确保账务与通知在可预期节点触发，便于审计与回滚。

## 后端接口设计（建议）
- 请求主体：
  - `POST /requests/create`（发布并冻结悬赏）
  - `GET /requests/list`、`GET /requests/:id`（查询）
  - `POST /requests/:id/update`、`POST /requests/:id/cancel`、`POST /requests/:id/increase-bounty`
- 认领与完成：
  - `POST /requests/:id/claim`（认领，支持幂等键）
  - `POST /requests/:id/link-torrent`（绑定 `torrentId/externalUrl/proof`）
  - `POST /requests/:id/verify`（请求者验收）
  - `POST /requests/:id/complete`（系统/版主结算）
  - `POST /requests/:id/dispute`（争议进入仲裁）
- 互动与订阅：
  - `POST /requests/:id/comment`、`GET /requests/:id/comments`
  - `POST /requests/:id/vote`（加权或去重策略）
  - `POST /requests/:id/subscribe`（站内信/邮件订阅）
- Bonus 联动：
  - `POST /bonus/freeze`（`refType=request, refId=requestId`）
  - `POST /bonus/release`（到期或取消）
  - `POST /bonus/payout`（完成结算至应答者）
- 原因：端点覆盖核心动作并与现有 `BonusService` 对齐，分离请求域与账务域，降低耦合与风险。

## 数据模型与表（建议）
- `requests`：主体（标题、描述、分类、状态、悬赏、创建者、到期时间、审核标记、当前认领者）
- `request_claims`：认领记录（认领者、时间、状态、幂等键）
- `request_submissions`：提交记录（`torrentId/externalUrl/proof`、快照、提交者、时间）
- `request_verifications`：验证记录（通过/拒绝、原因、验证者、时间）
- `request_comments`：评论（去重与敏感词审查字段）
- `request_votes`：投票（用户→请求唯一约束）
- `request_events`：事件表（用于审计与重放）
- `request_settlements`：结算流水（冻结/发放/解冻/退款/手续费，关联 `bonus_ledger`）
- 原因：事件化与分表，便于审计、回溯与性能扩展，账务与业务边界清晰。

## 前端改造方案
- API 封装：新增 `src/api/custom/requests.ts`，沿用 `bonus.ts` 封装风格（`OpenAPI` + `__request` + `unwrap`）。
- Hooks：`useRequestsList/useRequestDetail/useCreateRequest/useClaimRequest/useLinkTorrent/useVerifyRequest/useIncreaseBounty/useComments/useVotes`，基于 `@tanstack/react-query`。
- 页面改造：在 `RequestsPage` 中替换静态数据为真实接口，按权限控制按钮显隐与禁用；所有提交提供成功/失败提示与重试策略。
- 交互补充：
  - 列表：筛选（状态/分类/关键字）、排序（时间/悬赏/热度）、订阅按钮。
  - 详情：认领、提交资源、请求者验收、发起争议、评论/投票、事件时间线。
  - 发布表单：悬赏范围校验、分类合法性校验、冷却期与信誉提示。
- 原因：保持现有三视图架构与组件库一致，逐步替换数据源，最小化改动风险并提升用户体验。

## Bonus 结算规则
- 冻结：发布时冻结悬赏；失败则回滚发布。
- 发放：`fulfilled` 后一次性转入应答者；可选按权重分摊（若多提交并被采纳）。
- 解冻：`expired/cancelled` 自动解冻返还请求者。
- 退款：仲裁不通过或违规撤销时退款并记录原因。
- 账务理由建议：`request_bounty_freeze|release|payout|refund|fee`。
- 原因：与站内积分一致的可追溯账务规范，保障用户信任与版主审计。

## 通知与订阅
- 触发点：`create/claim/submit/verify/complete/expire/dispute`。
- 渠道：站内信（必须）、邮件（可选）、Web 推送（后续）。
- 订阅：请求者默认订阅；其他用户可手动订阅详情更新。
- 原因：提升协作效率与响应速度，降低漏处理风险。

## 风控与合规
- 发布节流与信誉门槛（最低悬赏、冷却时间、历史完成率门槛）。
- 重复检测与近似匹配提示（标题/描述相似度、分类一致性）。
- 敏感词过滤与内容审核（描述与评论）。
- 并发与幂等（认领/提交动作要求幂等键，防重入）。
- 原因：抑制滥用与刷分，保障社区秩序与合规性。

## 审计与日志
- 事件化记录所有关键动作，便于版主仲裁与问题回溯。
- 与现有 `AuditService`/`ActivityService` 对齐，统一查询口径。
- 原因：追责与风控的基础设施，便于监控与数据分析。

## 指标与监控
- 关键指标：发布量、认领率、完成率、平均完成时长、争议率、退款率、悬赏使用率。
- 异常告警：认领后长期未提交、提交后长期未验证、异常高争议率。
- 原因：数据驱动优化流程与策略。

## 测试与验收
- 单元测试：接口入参校验、状态机流转、账务计算。
- 集成测试：端到端“发布→完成”闭环、并发认领、仲裁分支。
- 前端测试：Hook 状态、错误提示、权限显隐、表单校验。
- 验收标准：覆盖核心流程，账务与通知无遗漏；回滚与审计可用。
- 原因：保障上线质量与回归稳定性。

## 迭代与发布建议
- Phase 1：发布/列表/详情/认领/提交（最小闭环，不含仲裁）
- Phase 2：验证/结算/解冻/退款/通知/审计
- Phase 3：风控/订阅/近似检测/指标与告警/仲裁台
- 原因：分阶段降低风险，确保尽快提供可用价值。
