# 接口错误提示规范（前端）

本文档定义当接口失败时，前端应如何提取错误、呈现提示与上报日志，以确保一致、可用、可国际化且可维护。

## 适用范围
- 所有通过 `src/api` 层发起的 HTTP 请求与业务操作
- React 组件内的表单提交、列表操作、上传下载等异步行为
- 用户认证与权限相关错误（401/403）统一处理

## 错误来源分类
- 网络层错误：断网、DNS、TLS、跨域、超时等
- HTTP 状态错误：4xx（客户端）、5xx（服务端）
- 业务错误：后端返回的业务码、`message`、`data.message` 等
- 取消/中断：用户主动取消请求

参考代码位置：
- `src/api/core/request.ts:252` 捕获状态码并抛出 `ApiError`
- `src/api/core/ApiError.ts:15` 标准错误对象结构
- `src/utils/errorMessage.ts:1` 统一错误文案提取
- `src/api/axiosInterceptors.ts:16` 处理 `401` 并重定向登录
- `src/hooks/useAsyncAction.ts:83` 基于响应优先级的错误提示

## 错误对象标准结构
前端处理时，统一视为如下形态（可能来自 Axios/自定义/ApiError）：

```ts
interface AppError {
  message?: string;            // 通用错误文案
  data?: {                 // Axios 风格响应体
    status?: number;
    statusText?: string;
    data?: any;                // 后端返回体
  };
  body?: any;                  // OpenAPI codegen 的 result.body
  request?: { url?: string };  // 请求 URL（便于日志关联）
}
```

## 文案提取规范
- 统一使用 `extractErrorMessage(err, fallback)` 提取文案
- 提取优先级：
  1. `err.body.data.message` 或 `err.body.data.msg`
  2. `err.body.message | err.body.msg | err.body.error_description | err.body.error`
  3. `err.response.data.data.message | err.response.data.message | err.response.data.msg`
  4. `err.message`
  5. `fallback`（调用方提供的兜底文案）

参考实现：`src/utils/errorMessage.ts:1`

## 呈现方式规范
- Toast（默认）：短操作反馈、非阻断
  - 成功：`customToast.success`（1.5s）
  - 失败：`customToast.error`（5.0s）
  - 加载：`customToast.loading`，完成后必须 `dismiss`
  - 位置：`src/hooks/useToast.ts`
- 表单内联错误：与具体字段绑定的校验错误，优先在控件附近显示
- 模态对话框：破坏性操作或需强确认的失败提示（如删除失败）
- 页面级占位：列表加载失败时，用占位+重试按钮替代整页数据

建议：能内联就内联；通用操作用 Toast；需确认用对话框；影响整页用占位。

## 特殊状态处理
- 401 未认证
  - 统一拦截器执行：清理令牌、派发 `authChange`、跳转登录并携带 `from`
  - 参考：`src/api/axiosInterceptors.ts:40`
- 403 无权限
  - 优先展示“权限不足”，可引导联系管理员；保留当前页
- 404 资源不存在
  - 列表场景：空态替代；详情场景：展示“资源不存在”，可返回上一页
- 5xx 服务端错误
  - 使用兜底文案“服务暂不可用，请稍后重试”，提供重试按钮
- 取消请求
  - 不提示；仅在调用方需要时记录为调试信息

## 交互与可用性
- 消息长度：不超过 50 字；避免技术细节（如堆栈、路径）
- 明确动作：尽量包含行动建议（如“请稍后重试”/“检查网络连接”）
- 不重复提示：同一操作只提示一次；避免同时出现内联与 Toast 冲突
- 可重试：失败场景尽量提供重试入口（按钮或刷新）
- 可国际化：错误文案走字典映射，避免硬编码

## 日志与上报
- 前端控制台仅在开发环境打印详细错误
- 生产环境通过埋点/监控上报：
  - 错误类型（网络/HTTP/业务）
  - 接口 URL、HTTP 方法
  - 状态码与业务码（如有）
  - 提示给用户的最终文案
  - 发生时间与用户上下文（隐私合规）

## 代码示例（带注释）

### 统一的异步操作封装
```ts
import { useAsyncAction } from '@/hooks/useAsyncAction';
import { extractErrorMessage } from '@/utils/errorMessage';

// 在组件内：对保存操作做统一的加载、成功与失败提示
const { execute, loading } = useAsyncAction({
  successMessage: '保存成功',       // 成功统一短提示
  loadingMessage: '正在保存...',     // 加载中可见
  // 可选：onSuccess / onError 回调
});

async function handleSave(data: any) {
  await execute(async () => {
    // 调用业务接口
    const result = await api.save(data);
    return result;
  });
}
```

### 手动捕获并提示
```ts
import { customToast } from '@/hooks/useToast';
import { extractErrorMessage } from '@/utils/errorMessage';

async function handleUpload(file: File) {
  const loadingId = customToast.loading('正在上传...');
  try {
    await api.upload(file);
    customToast.dismiss(loadingId);     // 结束加载提示
    customToast.success('上传成功');     // 成功提示（短）
  } catch (err: any) {
    customToast.dismiss(loadingId);     // 避免同时存在 loading 与 error
    const msg = extractErrorMessage(err, '上传失败'); // 按优先级提取文案
    customToast.error(msg);             // 失败提示（长）
  }
}
```

## 文案与字典规范
- 后端建议字段：
  - 顶层：`code`（业务码）、`message`、`path`、`timestamp`
  - `data`：可选的 `message` 与 `bizcode`
- 前端字典：
  - 将常见业务码映射为用户友好文案（可按模块拆分）
  - 默认走后端 `message`，未匹配时使用字典兜底或操作级 fallback

## 落地要求
- 新增操作均使用 `useAsyncAction` 或上述模式
- 错误文案统一使用 `extractErrorMessage`
- 禁止在生产环境泄露技术细节到用户提示
- 401 重定向逻辑通过拦截器统一维护
- 列表/详情页对失败场景提供占位与重试
